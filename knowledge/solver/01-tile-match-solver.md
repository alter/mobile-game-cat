# Решатель для игр типа «куча слоёв + полка на 9 мест»

Дата сбора материала: 2026-08-24.

Механика: куча из 30–60 предметов, наложенных слоями (доступны только верхние, не перекрытые предметы); игрок переносит доступный предмет на полку из 9 мест; три одинаковых предмета на полке исчезают; поражение — полка заполнена без совпадений или кончились ходы; победа — куча разобрана полностью. Это механика игр «Sheep a Sheep» (羊了个羊), «Triple Match 3D», «Tile Busters», «Zen Match».

## Кратко

- Строгая теорема о NP-полноте именно этой механики (куча со слоями + ограниченная полка) в открытых источниках не найдена. Ближайшая по конструкции строго доказанная задача — Mahjong Solitaire (тоже слои, тоже перекрытие, но снятие идёт парами, без ограниченного буфера) — доказана NP-полной несколькими независимыми работами: [de Bondt, 2012](https://arxiv.org/abs/1203.6559) и [van Rijn / Hoogeboom / Kosters / Vis, 2012–2014](https://arxiv.org/pdf/1604.05487).
- Игра с ограниченным буфером (полка/резерв, как в нашей механике) структурно ближе к FreeCell-солитеру, для которого NP-полнота доказана при **любом фиксированном числе резервных ячеек** ([Helmert, 2003](https://www.sciencedirect.com/science/article/abs/pii/S0004370202003648)) — это прямой формальный аналог «полки на 9 мест».
- Родственная задача SameGame/Clickomania (снятие групп одинаковых плиток) тоже NP-полна, но при других ограничениях (2 столбца и 5 цветов, либо 5 столбцов и 3 цвета) — см. [Biedl, Demaine et al., 2002](https://arxiv.org/abs/cs/0107031) и усиление в [Demaine et al., 2015](https://erikdemaine.org/papers/Clickomania_MOVES2015/paper.pdf).
- При 30–60 предметах и полке на 9 мест полный перебор (BFS/DFS без отсечений) не сходится за разумное время: ветвление на каждом ходу ограничено числом видимых предметов (обычно 3–8), но глубина партии — десятки ходов, а состояние включает и содержимое кучи, и содержимое полки.
- Практически применим поиск в глубину с возвратом (depth-first search с backtracking) с мемоизацией уже просмотренных состояний, канонической формой состояния для ключа кэша и эвристическим порядком перебора ходов — так устроены открытые решатели Mahjong Solitaire, включая практический алгоритм из работы де Бондта.
- Порождение заведомо проходимых уровней — обратным ходом (reverse construction): берём собранную кучу (пустое поле), «раздаём» предметы в обратном порядке снятия. Приём подтверждён в статьях о генерации solitaire-раскладов ([Dan Q, FlipFlop Solitaire](https://danq.me/2026/04/18/flipflop-solitaires-deck-generation-secret/)) и реализован в открытых генераторах Mahjong Solitaire, например [dAmihl/MyJong](https://github.com/dAmihl/MyJong) (режим «always-solvable») и косвенно в [cchaiyatad/mahjong-solitaire-solver](https://github.com/cchaiyatad/mahjong-solitaire-solver).
- Число предметов каждого вида обязано быть кратно трём — иначе один-два «хвостовых» предмета невозможно снять никогда, и уровень гарантированно непроходим при любой игре.
- Эвристики «разумной игры» (не идеального решателя, а правдоподобного человека) документированы фрагментарно: разборы Zen Match и Tile Busters описывают эффект скрытых слоёв («слепые» ходы), а открытый решатель [NB-Dragon/SheepSolver](https://github.com/NB-Dragon/SheepSolver) реализует несколько стратегий выбора хода (по индексу, по слою, по «нормальному» прогрессу, случайно) — это ближе всего к формализации «жадного игрока» в открытом коде.
- Реальных решателей и генераторов именно под связку «слои + буфер на N мест» (Sheep a Sheep, Triple Match 3D) с открытым кодом почти нет; есть один backtracking-решатель на Python ([NB-Dragon/SheepSolver](https://github.com/NB-Dragon/SheepSolver)) и один RL-агент ([opendilab/DI-sheep](https://github.com/opendilab/DI-sheep)). Основная масса открытого кода — по Mahjong Solitaire (парное снятие, без буфера).

## 1. Формальная постановка задачи

### 1.1 Представление кучи: слои и перекрытия

В формальном определении Mahjong Solitaire, которое дают [Hoogeboom, Kosters, van Rijn и Vis](https://arxiv.org/pdf/1604.05487) (раздел 3.1 их статьи), конфигурация — это множество позиций `(i, j, k)`, где `i, j` — координаты в плоскости, а `k` — высота (слой). Заданы два условия целостности:

1. если `(i, j, k)` и `(i, j', k)` в конфигурации и `j < j'`, то все промежуточные `(i, j'', k)` тоже в конфигурации (нет дыр внутри ряда);
2. если `(i, j, k)` в конфигурации и `k > 0`, то `(i, j, k-1)` тоже в конфигурации (плитка не может висеть в воздухе — под ней должна быть опора).

Позиция `(i, j, k)` считается **скрытой** (hidden), если существует `(i, j, k+1)` — то есть сверху лежит другая плитка; иначе позиция **видимая** (visible). Позиция «доступна» (available), если она не скрыта и хотя бы одна из соседних по ряду позиций `(i, j-1, k)` или `(i, j+1, k)` отсутствует в конфигурации либо тоже свободна — то есть плитку можно «вынуть вбок». Эта формализация напрямую переносится на нашу механику: «куча слоёв» — то же самое трёхмерное (или произвольно-графовое) представление, где доступность определяется тем, что сверху ничего не лежит, а не боковым «выниманием».

Для нашей игры удобнее не привязываться к решётке `(i, j, k)`, а держать явный **направленный граф зависимостей** `blocked_by`: у каждого предмета есть множество идентификаторов предметов, которые лежат поверх него и должны быть убраны раньше. Это обобщение того же принципа перекрытия, которое использует открытый клон 羊了个羊, описанный в разборе [阮一峰 (Ruan Yifeng)](https://www.ruanyifeng.com/blog/2022/10/sheep-n-sheep.html): «поле делится на несколько наложенных слоёв со случайными позициями и типами карт на каждом слое, кликабельны только карты слоя без верхних перекрытий» (пересказ статьи).

```python
from dataclasses import dataclass, field

@dataclass
class Item:
    item_id: int
    kind: int                    # тип предмета (для матчинга по тройкам)
    blocked_by: set[int] = field(default_factory=set)   # id предметов сверху

@dataclass
class Pile:
    items: dict[int, Item]       # item_id -> Item, включая уже снятые (кроме удалённых)

    def is_available(self, item_id: int) -> bool:
        item = self.items[item_id]
        return len(item.blocked_by) == 0

    def available_items(self) -> list[int]:
        return [iid for iid, it in self.items.items() if self.is_available(iid)]
```

### 1.2 Состояние игры, ход, цель

Состояние `S = (Pile, Shelf, moves_left)`, где:

- `Pile` — оставшаяся куча (множество ещё не снятых предметов и граф `blocked_by`);
- `Shelf` — содержимое полки: мультимножество видов предметов, `|Shelf| <= 9` (или другой лимит);
- `moves_left` — остаток ходов, если он ограничен правилами уровня (не во всех клонах есть лимит ходов; в «Sheep a Sheep» лимита ходов формально нет, есть только лимит полки).

Ход: выбрать доступный (`is_available`) предмет из `Pile`, переложить его в `Shelf`. После перекладывания, если в `Shelf` набралось три предмета одного вида — они исчезают (это не выбор игрока, а автоматическое правило). Игра проиграна, если `|Shelf| == 9` и после последнего хода тройки не образовалось. Игра выиграна, если `Pile` пуста.

```python
def apply_move(state: "State", item_id: int) -> "State":
    assert item_id in state.pile.available_items()
    new_pile = state.pile.remove(item_id)          # снимаем с кучи, снимаем блокировки с того, что было под ним
    kind = state.pile.items[item_id].kind
    new_shelf = state.shelf.add(kind)               # кладём на полку
    new_shelf = new_shelf.resolve_triples()          # автоматически убираем тройки
    return State(pile=new_pile, shelf=new_shelf)

def is_win(state: "State") -> bool:
    return state.pile.is_empty()

def is_loss(state: "State") -> bool:
    return len(state.shelf) >= 9 and not state.pile.available_items()
```

## 2. Вычислительная сложность

### 2.1 Что доказано про Mahjong Solitaire (ближайшую строго изученную механику)

Строгих работ именно про «Sheep a Sheep» / «Triple Match 3D» / игры с полкой на N мест в открытых источниках (журналы, arXiv, конференции) не найдено — ближе всего по конструкции (слои, перекрытие, доступность только верхних предметов) стоит Mahjong Solitaire, для которой есть несколько независимых результатов:

- [Condon, Feigenbaum, Lund, Shor, 1997] — по пересказу в [Hoogeboom et al.](https://arxiv.org/pdf/1604.05487), доказали, что вариант игры с **неполной информацией** (игрок не знает заранее, что лежит под верхними плитками) — PSPACE-полон.
- [Eppstein, 2012] — по тому же пересказу, сформулировал доказательство, что вариант с **полной информацией** (все плитки видны игроку с начала) NP-полон.
- [de Bondt, «Solving Mahjong Solitaire boards with peeking», 2012, arXiv:1203.6559](https://arxiv.org/abs/1203.6559) — независимо доказал NP-полноту версии с полной информацией («peeking») сведением от 3-SAT, причём NP-полнота сохраняется даже если допустить только изолированные стопки высоты 2 форм `/aab/` и `/abb/`. Там же показано, что раскладки, состоящие только из изолированных стопок высоты 1 и 2, всегда разрешимы «с подглядыванием» и это решается за полиномиальное время (задача в классе P), и дан оптимальный алгоритм для таких раскладок без подглядывания.
- [Hoogeboom, Kosters, van Rijn, Vis, «Acyclic Constraint Logic and Games», ICGA Journal, 2014, arXiv:1604.05487](https://arxiv.org/pdf/1604.05487) — дают формальное определение конфигурации Mahjong Solitaire (см. раздел 1.1 выше) и независимо подтверждают NP-полноту сведением от Acyclic Bounded Nondeterministic Constraint Logic (Bounded NCL) — конструктивным сведением через «гаджеты» AND/OR/FANOUT/CHOICE. В этой же статье тем же приёмом доказана NP-полнота обобщённого Klondike-солитера.
- Магистерская диссертация [van Rijn, «Playing Games: The complexity of Klondike, Mahjong, Nonograms and Animal Chess», LIACS, Universiteit Leiden, 2012](https://theses.liacs.nl/398) — в абстракте прямо утверждается: «We present a proof that both Klondike and Mahjong are NP-complete, by reduction from Bounded Nondeterministic Constraint Logic» (пруф отрывка получен через открытие PDF диссертации).
- [de Bondt, «Solving Shisen-Sho boards», arXiv:2010.09014](https://arxiv.org/abs/2010.09014) — родственная игра (снятие пар одинаковых плиток, соединённых путём не более чем из трёх отрезков), тоже доказана NP-полной; попутно показано, что при реалистичных допущениях проверка «можно ли разыграть данную пару» вычислима за логарифмическое время.

### 2.2 Родственная механика с ограниченным буфером — FreeCell

Наша механика содержит существенный элемент, которого нет в классическом Mahjong Solitaire: **ограниченный внешний буфер** (полка на 9 мест), в который откладываются предметы про запас. Формально это ближе к пасьянсу FreeCell, где есть фиксированное число свободных ячеек для временного хранения карт. [Helmert, «Complexity results for standard benchmark domains in planning», Artificial Intelligence 143(2), 2003](https://www.sciencedirect.com/science/article/abs/pii/S0004370202003648) доказал, что определение выигрышности FreeCell NP-полно **для любого фиксированного положительного числа свободных ячеек** — то есть ограниченность буфера сама по себе не делает задачу полиномиальной. Прямого текста статьи через WebFetch открыть не удалось (сайт закрыл доступ), формулировка приведена по пересказу в независимых работах, которые её цитируют и используют как образец доказательства (например, [«Spider Solitaire is NP-Complete», arXiv:1110.1052](https://arxiv.org/abs/1110.1052), прямо ссылающейся на раздел 4.3 работы Хелмерта как на образец конструкции доказательства). Это структурный аналог: буфер на 9 мест в нашей игре играет ту же роль, что резервные ячейки в FreeCell.

### 2.3 Родственная механика без буфера — SameGame/Clickomania

Ещё одна близкая по духу (снятие групп одинаковых плиток) задача — SameGame (она же Clickomania): игрок убирает связную группу из двух и более одинаковых плиток, верхние падают вниз. [Biedl, Demaine, Demaine, Fleischer, Jacobsen, Munro, «The Complexity of Clickomania», 2002 (arXiv:cs/0107031)](https://arxiv.org/abs/cs/0107031) доказали, что определение разрешимости (можно ли снять все плитки) NP-полно для двух столбцов и пяти цветов либо для пяти столбцов и трёх цветов, тогда как один столбец с двумя цветами решается за линейное время. Более позднее усиление — [«Clickomania is Hard, Even with Two Colors and Columns», MOVES 2015](https://erikdemaine.org/papers/Clickomania_MOVES2015/paper.pdf) — показывает NP-полноту уже для двух цветов и двух столбцов (в версии со счётом). Эта механика структурно дальше от нашей (нет слоёв и нет буфера, снятие идёт по смежности на плоскости, а не по типу с ограничением «три штуки»), поэтому её стоит рассматривать лишь как ещё один пример: у семейства «убери одинаковые плитки» вычислительная сложность в общем случае высокая, и ни один из вариантов не оказался полиномиальным без сильных ограничений.

### 2.4 Честный вывод

Для точной механики задания — куча со слоями, доступность только верхних предметов, ограниченный буфер на 9 мест, снятие тройками — строгого доказательства NP-полноты (или принадлежности P) в открытых научных источниках не найдено. То, что реально доказано:

- Mahjong Solitaire (слои + перекрытие, снятие парами, без буфера) — NP-полна ([de Bondt, 2012](https://arxiv.org/abs/1203.6559); [Hoogeboom et al., 2014](https://arxiv.org/pdf/1604.05487); тезис [van Rijn, 2012](https://theses.liacs.nl/398)).
- FreeCell (ограниченный буфер, без слоёв) — NP-полна при любом фиксированном размере буфера ([Helmert, 2003](https://www.sciencedirect.com/science/article/abs/pii/S0004370202003648)).
- SameGame/Clickomania (снятие связных групп одинаковых плиток, без слоёв и без буфера) — NP-полна при определённых ограничениях на число столбцов и цветов ([Biedl et al., 2002](https://arxiv.org/abs/cs/0107031); [Demaine et al., 2015](https://erikdemaine.org/papers/Clickomania_MOVES2015/paper.pdf)).

Поскольку наша механика объединяет оба «тяжёлых» ингредиента (слои со скрытием, как в Mahjong, и ограниченный буфер, как в FreeCell), разумно предполагать (но не доказано в найденных источниках!) NP-полноту и для неё. Утверждения из GitHub-репозитория [NB-Dragon/SheepSolver](https://github.com/NB-Dragon/SheepSolver) о том, что решение «羊了个羊» — это «NP-задача», — это неформальная реплика автора-энтузиаста в README, а не результат рецензируемой работы; в тексте задания эту формулировку заменять строгим доказательством нельзя, и мы этого не делаем.

## 3. Алгоритмы поиска

Практическая сторона задачи (не доказательство сложности, а собственно решатель) при 30–60 предметах и полке на 9 мест выглядит так: пространство состояний огромно, но ветвление на каждом ходу мало (выбор среди «доступных» предметов, обычно от 1 до 8–10 штук одновременно), а глубина партии равна числу предметов в куче. Это классическая постановка для перебора с отсечениями, а не для «грубой силы».

- **Поиск в ширину (BFS).** Гарантирует кратчайшее решение по числу ходов, но требует хранить весь фронт состояний — при ветвлении даже 3–4 и глубине 40–60 ходов фронт растёт на порядки быстрее, чем позволяет память. Практически неприменим без агрессивного отсечения дублей.
- **Поиск в глубину с возвратом (DFS/backtracking).** Основной инструмент для такого рода задач: на каждом шаге пробуем один из доступных ходов, рекурсивно решаем остаток, при неудаче — откатываемся и пробуем следующий. Именно так устроен практический алгоритм де Бондта для Mahjong Solitaire (сформулирован как «простой и быстрый», с «эффективным критерием отсечения и эвристикой для нахождения и приоритезации критических групп», по описанию из аннотации [arXiv:1203.6559](https://arxiv.org/abs/1203.6559)), и так же устроен открытый решатель [NB-Dragon/SheepSolver](https://github.com/NB-Dragon/SheepSolver) для «Sheep a Sheep» — в его README алгоритм прямо назван «поиском с возвратом» (backtracking).
- **A\* с эвристикой.** Применим, если задача — не «пройдено/не пройдено», а «минимальное число ходов»: тогда нужна допустимая (не переоценивающая) эвристика, например «число ещё не собранных троек» или «число видов, у которых на куче осталось меньше 3 штук доступных прямо сейчас». Для чистой проверки проходимости A* избыточен — обычно достаточно DFS с отсечениями; A* оправдан, если параллельно нужен ответ на вопрос «за сколько ходов при идеальной игре».
- **Итеративное углубление (iterative deepening / IDDFS, а для A* — IDA\*).** Полезно, если заранее неизвестна разумная глубина/лимит по числу ходов и важно не тратить память на полный фронт BFS: повторяем DFS с растущим порогом глубины (или растущим порогом стоимости для IDA*), пока не найдём решение или не докажем его отсутствие в пределах бюджета.

Для чистой проверки «проходим ли уровень» практичнее всего DFS с возвратом и жёсткими отсечениями (раздел 4). Для оценки «за сколько ходов при разумной игре» — не полный поиск, а один прогон жадного эвристического игрока (раздел 5), возможно, усреднённый по нескольким запускам со случайными допустимыми вариациями порядка ходов.

```python
def solve_dfs(state: "State", seen: set, limit: int | None = None) -> list[int] | None:
    """Depth-first search with backtracking. Returns a winning move sequence or None."""
    key = state.canonical_key()
    if key in seen:
        return None                      # already proven a dead end from this state
    if state.is_win():
        return []
    if state.is_loss():
        seen.add(key)
        return None
    if limit is not None and limit <= 0:
        return None

    for item_id in ordered_candidate_moves(state):   # move ordering, see section 4
        next_state = apply_move(state, item_id)
        rest = solve_dfs(next_state, seen, None if limit is None else limit - 1)
        if rest is not None:
            return [item_id] + rest

    seen.add(key)                        # memoize: this state is a proven dead end
    return None
```

## 4. Отсечения, без которых поиск не сходится

- **Мемоизация уже просмотренных состояний.** Без запоминания «из этого состояния решения нет» DFS будет заново пересчитывать одни и те же тупики, до которых можно дойти разными порядками ходов (перестановочность независимых ходов — классический источник взрыва числа повторов). Хранить нужно не саму последовательность ходов, а **состояние** (содержимое кучи + содержимое полки) в множестве уже доказанных проигрышей.
- **Канонический вид состояния для ключа кэша.** Полка — мультимножество видов, а не последовательность: порядок предметов на полке не имеет значения для дальнейшей игры (кроме, возможно, UI), поэтому ключ должен нормализовать полку (например, отсортированный кортеж видов) и отдельно — оставшуюся часть кучи (frozenset id ещё не снятых предметов достаточно, так как граф `blocked_by` однозначно вычисляется из множества оставшихся id и исходной структуры кучи).
- **Отсечение по заведомо проигрышным состояниям.** Помимо буквального «полка заполнена без совпадений», полезны более ранние необходимые условия невозможности выигрыша, например: если какой-то вид предмета имеет на кучe число оставшихся штук, не кратное трём после исключения уже снятых — уровень непроходим в принципе (см. раздел 7); можно проверять это как инвариант уровня один раз при загрузке, а не на каждом узле поиска.
- **Порядок перебора ходов (move ordering).** DFS находит решение быстрее, если сначала пробовать ходы, которые с высокой вероятностью полезны: например, в первую очередь брать предмет, если на полке уже лежат два предмета этого же вида (тогда ход сразу же освобождает место на полке), и только потом — прочие доступные предметы. Такой порядок резко уменьшает средний коэффициент ветвления на практике, хотя формально не меняет корректность поиска.

```python
def ordered_candidate_moves(state: "State") -> list[int]:
    """Heuristic move ordering: prefer moves that complete a triple right away,
    then moves that make progress on a pair already on the shelf,
    then everything else, biased toward items with fewer remaining copies."""
    available = state.pile.available_items()

    def priority(item_id: int) -> tuple:
        kind = state.pile.items[item_id].kind
        count_on_shelf = state.shelf.count(kind)
        remaining_of_kind = state.pile.remaining_count(kind)
        completes_triple = 1 if count_on_shelf == 2 else 0
        return (-completes_triple, -count_on_shelf, remaining_of_kind)

    return sorted(available, key=priority)
```

## 5. Эвристики «разумной игры» (жадный игрок)

Открытых формальных публикаций о том, как именно моделировать «правдоподобного человека» именно для игр вида «куча + полка», немного; собранное ниже — то, что реально нашлось в разборах и в открытом коде, без додумывания.

- **[NB-Dragon/SheepSolver](https://github.com/NB-Dragon/SheepSolver)** реализует не один, а несколько вариантов стратегии выбора карты для снятия («抽牌策略», стратегия вытягивания карт): по индексу по возрастанию/убыванию, по слою (сначала нижние/сначала верхние), «нормальный» режим (зависит от прогресса partии) и случайный режим. Разные стратегии дают разную эффективность решения — то есть сам автор явно фиксирует, что порядок хода критичен для результата, а не только сам факт «есть решение».
- Разбор Zen Match от [Deconstructor of Fun](https://www.deconstructoroffun.com/blog/2023/10/15/zen-match-how-a-first-mover-falls-behind) прямо указывает на источник субоптимальности человеческой игры: скрытый слой заставляет игрока делать «слепые» ходы («since Tile Match is a pretty deterministic genre, anything that the player can't see increases the difficulty» — жанр детерминирован, поэтому именно то, что игрок не видит, повышает сложность). Разбор Tile Busters от [Gamigion](https://www.gamigion.com/game-analysis-spyke-games-tile-busters/) подтверждает тот же эффект: «hidden tiles encourage players to make blind guesses, introducing a chance factor». Формально это означает, что модель «разумного игрока» обязана либо не видеть содержимое кучи ниже верхнего слоя (то есть строить решение по неполной информации — ближе к постановке Кондона и др., PSPACE, раздел 2.1), либо явно моделировать угадывание случайным выбором среди накрытых предметов.
- Общий принцип «жадности», который следует из механики автоматического снятия троек (не из отдельной публикации, а прямо из правил игры, формализованных в разделе 1.2): игроку невыгодно брать предмет вида, которого уже на полке нет и не предвидится третьей копии в ближайших доступных слоях, если свободных мест на полке мало — потому что это приближает поражение без выгоды. Отсюда естественная (и наиболее часто встречающаяся в реализациях-клонах troubleshooting-статей вроде разбора [Ruan Yifeng](https://www.ruanyifeng.com/blog/2022/10/sheep-n-sheep.html)) жадная эвристика: `priority(item) = -(2, если довершает тройку; 1, если на полке уже есть хотя бы одна копия; 0 иначе)`, с приоритетом видов, у которых после хода останется ровно кратное трём число экземпляров.

```python
def greedy_human_move(state: "State", rng) -> int | None:
    """A plausible-human policy, not an optimal solver.
    Prefers: (1) complete a triple now, (2) add to an already-started pair,
    (3) otherwise avoid moves that would fill the shelf without progress,
    falling back to a blind (random) choice among visually identical covered items
    to emulate imperfect information about what is still buried."""
    available = state.pile.available_items()
    if not available:
        return None

    def score(item_id: int) -> tuple:
        kind = state.pile.items[item_id].kind
        on_shelf = state.shelf.count(kind)
        free_slots = 9 - len(state.shelf)
        risky = 1 if (on_shelf == 0 and free_slots <= 2) else 0
        return (-(on_shelf == 2), -(on_shelf == 1), risky)

    best_score = min(score(i) for i in available)
    best_moves = [i for i in available if score(i) == best_score]
    return rng.choice(best_moves)          # tie-break emulates human blind pick
```

Оценка «за сколько ходов пройдёт человек» технически считается не запуском решателя, а прогоном такого жадного игрока (возможно, многократным с разными `rng`, чтобы получить распределение числа ходов, а не одно число) — в противоположность «идеальному решателю» из разделов 3–4, который ищет вообще любое решение или кратчайшее решение.

## 6. Порождение заведомо проходимых уровней обратным ходом

Это ключевой приём: вместо «сгенерировать случайную кучу → проверить решателем → отбросить, если не проходится» (генерация-и-проверка, дорогая при NP-полной по предположению задаче) строим кучу **в обратном порядке снятия**. Берём полностью разобранную кучу (пустое поле) и «раздаём» предметы назад, шаг за шагом выполняя операции, обратные ходу игрока; тогда сама последовательность раздачи — уже готовое решение, и проходимость гарантирована по построению, а не по проверке.

- Статья [Dan Q, «FlipFlop Solitaire's Deck-Generation Secret», 2026](https://danq.me/2026/04/18/flipflop-solitaires-deck-generation-secret/) формулирует приём в общем виде для пасьянсов: «start with a “solved” deck… and perform a randomly-selected series of valid reverse-moves» — начать с разложенной по правилам победы колоды и применить случайную последовательность обратных ходов; автор прямо называет это переводом задачи «проверить, что расклад выигрышен» (NP-трудная в общем случае) в задачу «построить выигрышный расклад» (полиномиальная, потому что мы сами выбираем шаги).
- Для Mahjong Solitaire этот же приём реализован в открытом коде: репозиторий [dAmihl/MyJong](https://github.com/dAmihl/MyJong) (Godot) явно предоставляет выбор между «полностью случайной раскладкой» и «всегда решаемой раскладкой» («always-solvable tile placement» — по описанию проекта); репозиторий [cchaiyatad/mahjong-solitaire-solver](https://github.com/cchaiyatad/mahjong-solitaire-solver) заявлен как генерирующий решаемую доску и решающий её тем же проходом на основе алгоритмов из работы Т. Стама «Solving Mahjong Solitaire Positions» (доступна по адресу `iivq.net/scriptie/scriptie-bsc.pdf`; открыть содержимое PDF через доступные инструменты не удалось — файл отдаётся в двоичном виде без пригодного для извлечения текста, поэтому детали её алгоритма здесь не пересказываются, только сам факт использования и статья, на неё ссылающаяся).
- Статья на Wikipedia про [Mahjong solitaire](https://en.wikipedia.org/wiki/Mahjong_solitaire) отдельно поясняет, зачем вообще нужна гарантия решаемости: «An analysis of ten million games with the default layout, ‘the turtle’, found that about 3 percent of the turtles cannot be solved even when looking below tiles is allowed» — то есть при чисто случайной раздаче классической раскладки около 3% партий не проходятся даже при полном знании о содержимом кучи; отсюда и практика «многие реализации не позволяют выигрышу быть невозможным даже с отменой хода» (там же).
- Общий академический обзор техник (не про Mahjong конкретно, а про процедурную генерацию головоломок в целом) выделяет обратный поиск (reverse search — «найти начальное состояние, сгенерировав решение заранее») как одну из трёх типовых стратегий генерации головоломок наряду с «сгенерировать-и-проверить» и прямой конструктивной генерацией с учётом ограничений; источник — обзор процедурной генерации головоломок, см. цитируемую в поиске работу об алгоритмах Wave Function Collapse и смежных методах для генерации головоломочных уровней (доступ подтверждён через веб-поиск, а не прямым чтением статьи, поэтому формулировка дана в общем виде без точной цитаты).

Применительно к нашей механике (слои + полка на 9 мест) обратный ход выглядит так: на каждом шаге «обратной раздачи» мы виртуально возвращаем один снятый предмет назад в кучу — либо на пустую (видимую) позицию, либо поверх уже размещённого предмета (создавая перекрытие), либо восстанавливаем тройку на полке, разбивая её обратно на три предмета и удаляя их с полки в кучу. Порядок этих обратных операций выбирается случайно (со смещением вероятностей под желаемую плотность перекрытий и глубину слоёв — см. раздел 8), а сама последовательность прямых ходов, обратная к порядку раздачи, и есть готовое доказательство проходимости.

```python
import random


def generate_solvable_pile(num_kinds: int, copies_per_kind: int, rng: random.Random) -> "Pile":
    """Reverse construction: start from an empty pile and 'undo' removals.
    copies_per_kind must be a multiple of 3 (see section 7)."""
    assert copies_per_kind % 3 == 0

    pool = []
    for kind in range(num_kinds):
        pool += [kind] * copies_per_kind
    rng.shuffle(pool)                       # order in which items will be "un-removed"

    pile = Pile.empty()
    open_positions: list[int] = []          # positions with no item on top yet

    for kind in pool:
        pos = choose_reverse_position(pile, open_positions, rng)  # see section 8 for density knobs
        pile = pile.place_item(pos, kind)
        open_positions = pile.recompute_open_positions()

    # The reverse order of `pool` (grouped by shelf-triples) is a certificate
    # that this pile is solvable: playing items in that order always wins.
    return pile
```

## 7. Кратность трём

Каждый вид предмета исчезает с полки только тройками. Если итоговое число экземпляров какого-то вида в куче не кратно трём, то после снятия всех полных троек останется один или два «хвостовых» экземпляра этого вида, которые никогда не смогут собраться в тройку — а значит, либо они физически не могут быть убраны из кучи (если куча должна быть разобрана полностью), либо они гарантированно займут место на полке до конца партии, приближая переполнение. И то и другое делает уровень непроходимым **при любой стратегии игры**, то есть это необходимое (хотя не единственное — граф перекрытий тоже должен быть согласован) условие проходимости, которое дешевле всего проверять один раз при генерации уровня, а не искать решателем. Этот вывод не требует ссылки на внешний источник — он прямо следует из формального правила «три одинаковых предмета исчезают» (раздел 1.2) и является чистой комбинаторикой (число, не кратное 3, не представимо суммой троек без остатка).

```python
def validate_multiple_of_three(pile: "Pile") -> None:
    from collections import Counter
    counts = Counter(item.kind for item in pile.items.values())
    bad = {kind: n for kind, n in counts.items() if n % 3 != 0}
    if bad:
        raise ValueError(f"Level is unsolvable by construction: counts not divisible by 3: {bad}")
```

При процедурной генерации уровня обратным ходом (раздел 6) это условие выполняется автоматически, если генератор кладёт предметы в кучу пакетами по три экземпляра одного вида (как в примере `generate_solvable_pile` выше — `copies_per_kind` явно проверяется на кратность 3 до генерации). Опасность в основном возникает не на этапе генерации, а на этапе **редактирования** уровня вручную (дизайнер руками подвинул/удалил один предмет) — сюда и нужен property-тест «после любой модификации число предметов каждого вида кратно 3», рассмотренный в файле `02-level-format-and-property-tests.md`.

## 8. Настройка сложности

Прямых научных работ по параметрам сложности именно для механики «куча + полка» нет; собранные ниже параметры — из разборов конкретных коммерческих игр этого жанра.

- **Число видов предметов и глубина слоёв.** Расширение браузерной версии Zen Match в Chrome Web Store прямо описывает свою прогрессию сложности: «difficulty increases with more tile types and stacked layers, with a layer mechanic where, from level 3 onward, tiles stack on top of each other» (по странице расширения [Zen Match — Tile Puzzle, Chrome Web Store](https://chromewebstore.google.com/detail/zen-match-tile-puzzle/ngbebofjmipghhicjloijdnjdnkkhlpd), пересказ через поиск).
- **Плотность перекрытий и скрытые слои.** Разбор [Deconstructor of Fun по Zen Match](https://www.deconstructoroffun.com/blog/2023/10/15/zen-match-how-a-first-mover-falls-behind) вводит понятие «Layer 3» — полностью скрытых от игрока плиток — и явно связывает их количество со сложностью: чем больше таких плиток, тем больше «слепых» ходов вынужден делать игрок; автор статьи прямо критикует Zen Match за то, что «populates Layer 3 much more than other Tile Match games», и рекомендует «depopulate Layer 3» как способ понизить искусственную, не соответствующую мастерству игрока сложность.
- **Обструкции (препятствия) как отдельный рычаг сложности**, независимый от чистого перекрытия слоёв: разбор [Gamigion по Tile Busters](https://www.gamigion.com/game-analysis-spyke-games-tile-busters/) перечисляет типы препятствий («grass, sticky gel, chains, curtains, frogs, and bombs», а также «crates, ice blocks, and chained tiles»), которые «not only conceal tiles but also limit the available space» — то есть управляют сложностью отдельно и от числа видов, и от глубины слоёв.
- **Запас ходов / инструменты-помощники как компенсирующий рычаг.** Официальная справка Zen Match описывает полку как ёмкость с лимитом заполнения («matching 3-of-a-kind in your tile holder… but overloading the tile holder ends the round», по [support.zenmatchgame.com](https://support.zenmatchgame.com/hc/en-us/articles/9516848294034-How-do-I-play-Zen-Match)); в браузерной версии на Chrome Web Store прямо указана и числовая ёмкость полки, и число вспомогательных инструментов на уровень: «7 slots and it's game over», «undo… 3 uses per level», «shuffle… 1 use per level».
- **Двухфазная структура уровня** как приём против слишком раннего фрустрирующего провала: разбор Zen Match отмечает, что «every level comes in two waves. The first wave is always very easy and can be solved in under a minute» — то есть сложность внутри одного уровня растёт по ходу партии, а не постоянна.
- **Метрика для тюнинга, а не только «проходим/не проходим».** Общая статья по левел-дизайну игр этого семейства ([Room8Studio, «Smart & Casual: How to Build Match 3 Games Level Design»](https://room8studio.com/news/smart-casual-the-state-of-tile-puzzle-games-level-design-part-1/)) советует «switching from the pass rate to defining a number of attempts per level» и отслеживать «average and median attempts» — то есть валидировать сложность не бинарным «решаемо ли», а распределением числа попыток/ходов у эмулированного (или реального) игрока, что прямо соответствует эвристическому прогону из раздела 5.
- Академическая работа про автоматическую валидацию сгенерированных уровней match-3, [«Improving Conditional Level Generation using Automated Validation in Match-3 Games» (Avalon), arXiv:2409.06349](https://arxiv.org/html/2409.06349v2), даёт количественный пример такой практики: детерминированный бот проигрывает каждый сгенерированный уровень 30 раз, получает бюджет в 39 ходов (при том, что дизайнерский лимит — 20 ходов, разница даёт запас на дальнейшую подстройку), и **медиана числа ходов бота по 30 прогонам** используется как численная мера сложности при обучении генеративной модели; авторы отмечают, что «случайный» бот проваливает все обучающие уровни в пределах 20 ходов, а их эвристический бот по результатам сопоставим с человеком-тестировщиком.
