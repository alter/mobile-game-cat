## Blocking

### 1. The conformance test fails on a clean run

`pytest tools/tests` → `ERROR conformance_test.py::test_csharp_and_python_agree`,
the bridge exits with code 150.

Cause: `build/solver-bridge/solver-bridge.csproj` is built for `net8.0`, while
only the .NET 10 runtime is installed on the machine. This only works when
`DOTNET_ROLL_FORWARD=Major` is manually set in the environment — that is, in
the shell the executor happened to be sitting in. Verified: with the
variable the test passes, without it it fails.

Commit `2e68e6e` announces "30 cases agree (3.1 done)," but task 3.1 doesn't
reproduce in a clean environment. The workaround stayed in the executor's
head, not in the project.

A one-line fix — in `solver-bridge.csproj`:

```xml
<RollForward>Major</RollForward>
```

Rule for the future: if work depends on an environment variable, it must be
recorded in the project or in the launch script. "I have it exported" is not
a completed task.

### 2. Conformance only checks wins

All 30 cases produce the outcome `win` — verified by recomputing: `{'win': 30}`.

The test is built such that it couldn't be otherwise: it generates a level,
**solves** it, skips the unsolvable ones (`if sol is None: continue`), and
replays the found solution on both sides. A solution by definition leads to
a win.

That means two of the three outcomes — `shelf_jammed` and `out_of_moves` —
have never once been checked against each other between C# and Python. And
these are exactly the places where implementations diverge most readily:
the order of the jam check, the moment the move counter decreases, behavior
on the last move.

Acceptance for 3.1 reads "same level yields same outcome in C# and Python" —
about all outcomes, not just one.

Cases with a deliberately losing move order need to be added: cutting off
the solution partway and finishing greedily into a jam, and taking a
deliberately insufficient move limit. Until this exists, task 3.1 can't be
considered closed.

## Significant, but not blocking

### 3. The move limit silently diverged from the MVP description

In `cat-shelter-mvp.md`, section 3: "Moves: limited per level (from 25 on
the first to 18 on the twelfth, for the same pile size)." Shipped: 44 on the
first, 38 on the twelfth.

**The executor is right on the merits.** A win is defined as "the pile is
fully cleared," each move removes exactly one item, the pile has 36 items —
so a level is inherently unbeatable in fewer than 36 moves, and the 25
recorded in the concept is impossible. One number in the document
contradicts another number in the same document.

But the choice was made silently. The prompt requires exactly the opposite:
"if the primary source contradicts what's recorded in the project's
documents — show the discrepancy, don't choose silently." This should have
been stopped and flagged, and `cat-shelter-mvp.md` should have been
corrected. Right now the project has two documents with mismatched numbers,
and the next executor will have to guess which one is right.

### 4. The meaning of the shelf was interpreted silently

The concept says "three cells of 3 spots each" and "three identical items
on the shelf — they disappear." This allows two readings: a match within
one shelf of three spots, or a match among all nine spots.

The second was chosen, and this is most likely correct — if the match had
to be within a shelf of three spots, the game would be nearly unbeatable,
and the genre's reference example works exactly this way. The complaint is
the same: the fork wasn't named.

Worse is something else: `SlotsPerRow` and `RowCount` remain in the code,
even though not a single line gives the rows any meaning — the match is
searched across all nine spots at once. Someone reading the code will
conclude the rows mean something. Either remove the constants or explain
with a comment that this is display layout only.

### 5. No check for multiples of three

Neither `Level` nor `Board` checks that the count of each item kind is a
multiple of three. This holds in the shipped levels, but nothing enforces
it.

The consequence is real: a win is defined as `_taken.Count == _entries.Count`,
i.e. "the pile is empty," with no regard for the shelf. A level with a
non-multiple-of-three set produces a win with items stuck on the shelf. The
knowledge base explicitly flags this
(`knowledge/solver/01-tile-match-solver.md`, the section on
multiples-of-three).

The check should go in `Level`'s constructor — the same place that already
rejects duplicate identifiers.

### 6. Order of checks in `TakeItem`

The jam is checked before the win:

```csharp
if (Shelf.IsFull) { Finish(ShelfJammed); return true; }
if (_taken.Count == _entries.Count) { Finish(Win); return true; }
```

If the last item taken both fills the shelf to nine and empties the pile at
the same time, a loss is declared even though the pile is cleared — which
by the concept is a win.

With multiple-of-three sets the case is unreachable, so it isn't a bug
today. But `tools/solver/rules.py` repeats the same order, and **the
conformance test will never catch this**: both sides will get it wrong the
same way. This is an inherent weakness of the "port plus cross-check"
approach — it checks agreement, not correctness. The knowledge base warned
about this (`knowledge/solver/02-level-format-and-property-tests.md`).

## A note on the concept, not the code

All twelve levels are structurally identical: 36 items, 6 kinds. Only the
move-budget slack changes, from 8 to 2. Formally task 3.4 is done — it
called for exactly this slack curve.

But the concept talks about a pile of 30–60 items, and difficulty that
varies through a single parameter produces twelve levels that feel
indistinguishable. The player will see not twelve rooms, but one room they
are asked twelve times in a row to clear faster and faster.

This is worth deciding before art goes onto the levels: whether to vary
pile size, number of kinds, and overlap density together with the move
count. Task 3.7 — five outside people playing the debug build — is exactly
what would show this, and it hasn't been done yet.
