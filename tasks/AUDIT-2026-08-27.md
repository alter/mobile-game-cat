# Audit of every `done` label without `verify:passed` — 2026-08-27

## Why this exists

`30-levels-solver/07-outsiders-playtest` was found carrying `status:done`
while its OUTCOME artefact — five written playtest answers — was five empty
forms. One proven-false label makes every unverified one a question, so all
31 tasks with `status:done` and `verify:` other than `passed` were checked
against their own OUTCOME by an independent context that wrote none of them.

The check was: read the task's OUTCOME, then look for the artefact it names —
the file, the class, the count, the screenshot. Not "does the work look done"
but "is the thing that OUTCOME promises actually there".

**Result: 20 supported, 7 partial, 3 waiting on a human, 1 unsupported.**

The two most serious were re-checked by hand afterwards and both held.

## What was found, ranked by what a false `done` costs

### 1. `60-shell-build/13-headless-build` — unsupported

OUTCOME: *"`build/headless-build.sh` run from a clean checkout produces a
signed .ipa and a non-zero exit code on any failure."*

`build/` contains `check-core-purity.sh`, `core-tests`, `coverage-summary.py`,
`playtest`, `solver-bridge`. There is no `headless-build.sh` and no `.ipa`
anywhere in the repository.

What *does* exist is real and useful: `BuildScript.BuildIOSXcodeProject` and
`BuildScript.BuildIOSSimulatorProject`, a working simulator run, and the whole
command sequence written down in `cat-shelter-tech.md` section 5. The task's
own NOTES say so plainly and also admit the device run was never made. So the
work is genuine; it is the deliverable that is not. Nobody can run one command
and get a signed build, and TestFlight and gate 3 both assume otherwise.

Label: `done` → `in_progress`.

### 2. `50-photo/07-crop-downscale` — partial

OUTCOME: *"A 512x512 JPEG, **base64-encoded**, under 200 KB before encoding,
ready to POST to /traits."*

The crop and the size ceiling are there — `Shell/CatPhoto.cs:17-18`,
`Side = 512`, `MaxBytes = 200*1024`. The base64 encoding is not:
`grep -rn "ToBase64String" game/Assets` returns one comment and no code, while
`worker/src/index.ts:77` requires an `image_base64` field.

**The wider fact this uncovers matters more than the label.** `AskWorker` in
`View/CaptureScreen.cs:36` is a delegate that nothing in the shipping code
ever assigns, so the app has never called the Worker at all — it always falls
through to the on-device colour estimate. That is not a false `done`: the call
belongs to `50-photo/08-capture-screen`, which is correctly `in_progress`. But
the path metric 2 measures ("uploaded a photo > 40%") has never run end to
end, and it is blocked behind the same account the Worker is.

Label: `done` → `in_progress`.

### 3. `60-shell-build/01-presentation-input` — partial, already disclosed

Click-to-take works; there is no drag and no animation anywhere in the UI
(`grep transition|animation game/Assets/View/DebugGame.uss` → nothing). The
task's own `verify:` line already says so. No change; listed for completeness.

### 4. `20-rules-core/05-coverage` — partial

OUTCOME: *"Coverage report produced by command, threshold enforced by the
build."* The report exists and is good — `coverage.cobertura.xml`,
`line-rate="0.9781"`. Nothing enforces it: there is no CI configuration, and
no script invokes `coverage-summary.py --min`. The 90% gate is a flag nobody
passes, so coverage can rot while the label says it cannot.

Label: `done` → `in_progress`.

### 5. `90-android/00-android-decision` — partial, self-disclosed

A dated go decision whose own text reads *"The task asks for gate-3 numbers by
value. **There are none.**"* It unblocks a whole P2 phase on judgement alone.
No change — the phase should not be worked before the gates anyway.

### 6. `60-shell-build/08-mid-level-save` — partial

OUTCOME: *"Board.Save()/Board.Load() round-trip losslessly, and a killed-and-
reopened app lands on the same position **on device**."* The round-trip exists
under different names — `Core/BoardSave.cs`, `Capture`/`Restore`, with tests.
The device half was never done on iOS. It *was* done on Android and
photographed (`90-android/11-save-parity/resumed.png`), which is evidence for
the mechanism but not for this task's platform.

Label: `done` → `in_progress`. The remaining work is one kill-and-reopen on a
phone, which lands with `14-testflight`.

### 7. `30-levels-solver/12-piles-per-room-curve` — partial

The pacing curve is written twice: `tools/solver/pacing.py:9
PILES_PER_ROOM = (1,2,3,3,3,3,3,3,4,4,4,4)` and `View/LevelAssets.cs:20-21`.
Two copies in two languages with nothing comparing them. Fixed by a test
rather than a label — see below.

### 8. `50-photo/10-skip-default-cat` — partial

OUTCOME: *"the same default cat every time, **named** and playable"*. The
default cat exists and is deterministic (`CatTraits.Default`, grey tabby,
`TraitsOrigin.Skipped`); there is no name field anywhere in `game/Assets`. The
naming half was never built.

Label: `done` → `in_progress`.

### 9–11. Waiting on a human, not on work

`20-rules-core/06-debug-view`, `60-shell-build/09-notification`,
`60-shell-build/10-click-haptics`. In all three the code is in place and the
acceptance needs a physical phone — a simulator has no Taptic Engine and
schedules no notifications. All three say so in their own notes. Left `done`
with `verify:pending`, which is the honest state; they resolve with
`14-testflight`.

Notification delivery is the one worth watching: it is unproven, and a
reminder that silently never fires is invisible until day-1 retention comes
back low for a reason nobody can see.

## The twenty that held

`10-accounts/03`, `20-rules-core/01`, `20-rules-core/03`,
`30-levels-solver/05`, `/06`, `/09`, `/10`, `/11`, `40-art/01`, `40-art/02`,
`50-photo/01`, `/05`, `/06`, `/11`, `60-shell-build/07`, `/12`, `/16`, `/17`,

hit, not against its own prose.

## What this says about the tree

Nineteen of twenty labels that could be checked mechanically were true. The
failures cluster in one place: **tasks whose OUTCOME requires something
outside the repository** — a signed build, a device in hand, a CI runner, a
network call to a service with no account. Those are exactly the ones an agent
cannot finish and exactly the ones where a `done` costs the most, because the
work downstream assumes them.

The rule that follows: an OUTCOME naming an artefact outside the repository
cannot be closed by the context that wrote the code for it. That is already
the `verify:` rule; what this audit adds is that `status:done` needs the same
discipline, because in practice `done` is what people read.
