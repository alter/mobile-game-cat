## What the failures have in common

### Yesterday's pattern still explains the waiting, but no longer the false

Yesterday's finding was that failures cluster in tasks whose OUTCOME lives
outside the repository. That still describes the **needs a person** bucket
exactly: all five want a phone, a human viewer, or an account, and not one of
them is an agent's to close.

It no longer describes the false ones. Of the three, **two are entirely inside
the repository**:

- `60-shell-build/01` asks for animation. There is no animation. Nothing about
  that needed a device, an account or another person — one `grep` over a
  293-line stylesheet settles it, and has settled it the same way for three days.
- `50-photo/01` asks for a committed folder. The folder is on this machine and
  not in the repository: `git ls-files` returns 4 of 41. To the context that
  built it, `ls` said forty-one and the claim looked true.

### The new shape: a claim that was true when written and was never re-read

This is what today's churn exposed. Four specimens, and they rhyme:

1. **`30-levels-solver/04`** — 98/87/66 was an honest measurement. The policy
   was re-derived, the numbers moved to 98.0/83.8/71.5, and the OUTCOME line
   still names the old ones. The NOTES.md beside it says so; the OUTCOME does not.
2. **`60-shell-build/03`'s `VERIFY.md`** — the clearest specimen in the tree. It
   cites a screenshot deleted six hours before I read it, and in one document
   both confirms `ios-numbers-in-order.png` and asserts it does not exist. A
   verification document rotted faster than the code it verified.
3. **`90-android/03`'s `level-1.png`** — the named artefact shows a build the
   art pass replaced. The verifier caught it and chose to keep it; the OUTCOME
   line was not updated to say which file it now means.
4. **`60-shell-build/17`'s `Info.plist`** — the count is right now, but the file
   it was counted from is a gitignored build artefact from yesterday evening.
   The next build could move it and nothing would notice.

The distinguishing feature is not that these live outside the repository. It is
that **nothing in the tree compares the claim to the thing it describes.** Where
such a comparison was written — `test_csharp_mirror_of_the_curve_still_agrees`,
`test_copy_table.py`, the coverage gate, `check-android-manifest.py` — the claim
held today under a command I ran myself. Where the only link is prose, it rotted
within a day.

### A second, quieter failure: seven `verify:passed` labels with no `VERIFY.md`

`tasks/README.md` makes the file a precondition: *"`verify:passed` requires a
`VERIFY.md` file in the task directory. Words in a commit message are not
evidence."* Seven do not have one:

`10-accounts/07-build-wiring-fix`, `20-rules-core` (phase),
`30-levels-solver/01-rules-in-solver`, `/02-solver`, `/03-level-generation`,
`/04-difficulty-curve`, `/08-measure-playtime`.

Six of the seven have OUTCOMEs I could confirm by running a command, so the work
is real and I have marked them true. But the label is unearned by the project's
own rule, and this is precisely the state `07-outsiders-playtest` was in when it
triggered the first audit: a green label with nothing under it to read. The one
that is not merely paperwork is `30-levels-solver/04`, where the absent
`VERIFY.md` is also the reason nobody noticed the numbers had moved.

### What went right, and it is most of the tree

Thirty-one of forty-two held under a command run today, and four of yesterday's
seven partials were closed rather than argued away: the coverage gate now exists
and fails when mutated, base64 encoding is in `TraitsRequest.cs`, the default cat
has a name, the plist count was recounted to 28, and `build/headless-build.sh` —
yesterday's single unsupported deliverable — is on disk with a signing stage that
exits non-zero rather than faking an `.ipa`.

The rule to add, in the shape of the two that already work:

**An OUTCOME that names a number, a count or a file is a claim that needs a
test, not a sentence.** Yesterday's rule kept agents from closing what they
cannot finish. This one keeps them from leaving true things behind that quietly
stop being true. Both failures inside the repository today would have been caught
by one assertion apiece — one that greps the stylesheet for a transition, one
that asks `git ls-files` how many photographs a fresh checkout gets.

## What I could not check, and why

- **Anything requiring Unity, the simulator or the emulator** — barred by the
  brief. So "compiles inside Unity" (`20-rules-core`) rests on the asmdef's
  `"noEngineReferences": true` and on the netstandard2.1 compile, not on a
  build; and every screenshot is evidence about the build that produced it, not
  about the tree as it stands after today's commits.
- **`build/headless-build.sh` end to end** — the command was refused by the
  permission layer. I ran its three test stages individually instead
  (`dotnet test`, `pytest tools/tests`, `coverage-summary.py --min 90`) and read
  the rest of the script; the Unity and signing stages are unexercised here.
- **"Uniform frame" on the 30 props, and every human-judgement item** — a
  machine can check 256×256 and RGBA, and did. It cannot check whether they look
  like a set.
